用了 Prisma 一周，我终于把手写 SQL 迁移的老毛病治好了

最新版 2026-10-16 ·约 9 分钟 ·老杨

从 Sequelize 切到 Prisma 的第一手体验：Schema 声明式建模、类型安全的查询 API、内省接入已有数据库，以及那些让我眼前一亮又有点懵的细节。

说实话，之前我对 ORM 是有偏见的。

项目里用过 Sequelize，也试过 TypeORM，每次都是一开始觉得"哇自动生成 SQL 好方便"，写到一半发现要调个复杂查询或者优化索引，又得绕回 raw query 里写原生 SQL。更头疼的是数据库迁移——团队里几个人各改各的模型文件，迁移文件生成得乱七八遭，合并分支的时候光解冲突就要花半小时。

所以这次新项目选技术栈的时候，我本来打算还是直接上 Kysely 这种 query builder，手写 SQL 起码心里踏实。正好那段时间Prisma官网也在推新版本，同事甩过来一段它的 Schema 文件让我看：

model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  posts Post[]
}

"就这？"我当时的反应是，"这能比 Kysely 强到哪去？"

事实证明我还是太年轻了。

第一天：装上就能跑，Schema 比想象中强

安装包从官方下载拿，或者直接走 npm：prisma 装 devDependencies，@prisma/client 装 dependencies。然后 npx prisma init 跑一下，它会帮你生成一个 prisma/schema.prisma 模板和一个 .env 文件，让你填数据库连接串。

我填了本地 PostgreSQL 的地址，然后开始写 Schema。这个过程让我有点意外——它不是简单把表结构翻译成 JSON，而是用了一种自己的 DSL 语法，model 块里能直接声明字段类型、默认值、唯一约束，还有 Prisma 级的关联字段。比如 User 模型里写 posts Post[]，数据库里不会真的多出一列，但 Prisma Client 生成的时候会给你 include posts 的能力。

最开始我以为这就是个高级点的类型声明文件，直到运行了 npx prisma migrate dev --name init。这条命令一口气做了四件事：读取 Schema → 生成一条带建表 SQL 的迁移文件 → 应用到数据库 → 自动 generate Prisma Client。一个命令搞定了我以前手动写的全部步骤，包括生成的 Client 居然是 TypeScript 类型安全的——这一点是 Sequelize 和 TypeORM 当年都没做到位的。

最惊喜的两个地方：查询真的舒服，迁移真的干净

查询 API 不是吹的

写第一个查询的时候我没抱太大期望，不就是个 findMany 吗？结果代码敲到一半发现不对——VS Code 自动补全了 include 参数，我选了 posts，立刻又跳出 where、orderBy、take、skip 一堆选项，而且 posts 里面的字段也跟着补全了。查的时候把 posts 关联数据一起拉下来，就是一行 include: { posts: true }。

这不是 ORM 的常规操作吗？但真正让我惊艳的是嵌套写入。创建一个用户同时创建他的第一篇文章，以前在 Sequelize 里得先 create user 拿到 id，再 create post 关联上去。Prisma 里直接这么写：

await prisma.user.create({
  data: {
    email: 'alice@example.com',
    posts: { create: { title: 'Hello Prisma' } },
  },
})

就一行。Prisma 自动处理了事务、外键关联、ID 传递。我第一次跑这段代码的时候盯着数据库里 User 和 Post 两表同时多出了记录，愣了两秒钟。

还有 findUnique 这种语义化的方法名——用 id 查就用 findUnique，返回值是单个对象或 null，不是 findFirst 那种可能返回第一条的语义。这些小细节加起来，让写查询的体验跟普通业务代码没什么区别，不像其他 ORM 总在"这到底会不会生成我想要的 SQL"这件事上让我焦虑。

迁移系统解决了我最痛的点

之前用 Sequelize 的时候，迁移文件是每次改 model 手动生成的，两个同事同时改 model 生成两条迁移，合并的时候就要小心调整顺序。而 Prisma 的 migrate dev 工作流是：你改 Schema → 跑 migrate dev → Prisma 对比差异生成新的迁移文件。迁移文件跟着代码一起进 Git，每个人拉下来都能 migrate dev 对齐本地数据库。

更重要的是开发和生产分了两条完全不同的命令。migrate dev 会读 Schema 并生成新迁移，而 migrate deploy 只应用 migrations 目录里已有的迁移，根本不碰 Schema。这意味着生产数据库永远只执行已经在开发环境审阅过的迁移文件——我以前最担心的"手滑在生产环境跑了开发命令"这种事故，从设计层面就被堵死了。migrate dev 和 migrate deploy 的完整区别在Prisma文档里有专门的对照表。

也有点懵的地方：内省让我"一键接手"了旧数据库

项目里还有一个老项目，用的是 TypeORM 建的库，我一直想把它迁到 Prisma 但觉得太麻烦。这次试了 db pull，一条命令直接把 PostgreSQL 里的表结构、外键、索引全翻译成了 schema.prisma。

它甚至帮我加上了 @map("table_name") 注解，处理了数据库表名是复数 snake_case 而 Prisma model 默认 PascalCase 的命名差异。跑 generate 之后直接就能用 Prisma Client 查老数据——整个过程不到十分钟。

不过有一个地方让我踩了坑。那个老库里有几张表用了存储过程做复杂查询，Prisma Client 不暴露这些，得用 $queryRaw 写原生 SQL。我当时以为 Prisma 能自动识别并封装，结果发现它的边界画得挺清楚：表结构和外键它管，视图、存储过程、触发器这些数据库一等公民之外的东西，要么自己写 raw query，要么迁移逻辑到应用层。

另外关系推断也不是百分百准确。老库里有一个多对多的中间表带了额外字段，Prisma 没把它识别成隐式多对多，而是当成了一个独立 model。这也合理——额外字段意味着中间表本身就是业务实体，不该被 Prisma 自动隐藏掉。我手动调整了 Schema 里的关系定义，跑了 generate，一切正常。

一周用下来，它适合谁

如果你正在新项目选 ORM，而且你的技术栈是 Node.js + TypeScript + 关系数据库，那 Prisma 基本没有理由不试——类型安全的查询、声明式的 Schema、干净的迁移流程，这三点加起来解决了 ORM 社区讨论了好几年的痛点。

如果你维护着一个老项目想换 ORM，db pull 让迁移成本比想象中低很多。但如果你的数据库里存储过程和触发器用得很重，那可能要重新评估——Prisma 不打算接管这些东西，它的设计哲学是让数据库做擅长的事、让应用层做擅长的事。

还有一点要提醒的是，Prisma Client 是 generate 出来的，Schema 改了要记得跑 npx prisma generate（migrate dev 会自动触发，但 db push 不会）。我第一天就因为忘了 generate 写了半天代码全是红线，这种小坑踩两次就记住了。

总之这一周的体验比预期好太多。以前我以为 ORM 就是"自动生成 SQL 的工具"，现在明白它其实可以是"用声明式语言描述数据模型的编译器"——Schema 是源代码，Client 是编译产物，迁移是版本化的数据库变更日志。这个思路一旦转过来，之前用其他 ORM 积累的那些"ORM 不可靠"的成见，好像也站不住脚了。我把这几天整理的笔记和示例代码同步放到了GitHub、Gitee 和 GitCode，想跑通一遍的可以直接 clone 下来试。
