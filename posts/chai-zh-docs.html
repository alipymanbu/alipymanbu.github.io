从堆满 console.log 的测试文件到三行断言——我是怎么被 Chai 拯救的

安卓版 2026-10-16 ·约 9 分钟 ·老杨

一个初级前端从用 console.log 人肉比对测试结果，到被 Chai 的链式断言语法彻底折服的真实经历。

上周三晚上十点，我盯着 VSCode 里那堆花花绿绿的 console.log，感觉眼睛要炸了。

事情是这样的：我在给公司那个用户反馈模块补单元测试，接口返回一堆嵌套对象，我就把每个字段都 console.log 一遍，然后对着 Expected 和 Actual 人肉比对错。跑一次测试，终端里刷屏几十行，关键是改错了又要从头看起——这种调试效率，搁谁谁崩溃。

同事路过我工位，看了一眼屏幕直接乐了：「你这是 2024 年的测试写法？试试 Chai 吧，就是个断言库，写起来像说话一样。」

我抱着试试看的心态搜了一下。Chai 是 Node.js 生态里最常用的断言库之一，配合 Mocha 跑测试套件。装起来也简单，从下载拿源码或者直接一条 npm install 都能搞定。而官网说它提供三种断言风格——expect、should、assert——让你挑自己觉得顺手的。

第一句代码就把我击中了

装好之后我写了个最简单的验证脚本：

const { expect } = require('chai');

expect(1 + 1).to.equal(2);
expect('hello').to.be.a('string');
expect([1, 2, 3]).to.have.lengthOf(3);

跑了一下 node verify-chai.js，没报错就是绿灯通过。然后我故意写错一个试试错误信息：

expect(1 + 1).to.equal(3);

终端直接给我一行清晰的 AssertionError：expected 2 to equal 3。没有满屏日志，没有乱八七糟的堆栈（默认关闭），就一句人话告诉我哪儿错了。

我当时的反应是——早说啊，这比我那堆 console.log 香太多了。

类型检查帮我踩了好几个坑

写了两天测试，我发现 Chai 在类型判断上做了很多贴心的处理，简直是帮新手防踩坑神器。

比如 JavaScript 那个著名的历史遗留 bug：typeof null 返回 'object'。Chai 不跟着犯傻，它有专门的判断：

expect(null).to.be.a('null');      // ✅ 正确
expect(null).to.be.an('object');   // ❌ 会失败

还有数组，虽然 typeof [] 也是 'object'，但 Chai 里数组就是数组，不会跟普通对象混为一谈：

expect([]).to.be.an('array');   // 通过
expect([]).to.be.an('object');  // 失败

这些小细节看着不起眼，但在写测试的时候能帮你省掉很多低级 bug。我之前就踩过一次——以为某个返回值是对象，结果是数组，用错误的方式遍历直接空数据，找了半天才发现是类型判断的问题。

那个 .not 让我纠结了一下

Chai 有个否定修饰器 .not，插在链式里就能反转断言结果。我一开始觉得这个挺好用的，写了一堆「不应该是这样」的断言。结果跑测试的时候发现一个问题——失败的时候错误信息不够有信息量。

举个例子，我之前写过：

expect(response.status).to.not.equal(500);

这个测试确实能通过，但问题是它也允许 status 是 404、302 甚至任意值。如果有一天接口真的返回了 404，这个断言照样绿灯，我压根不会注意到。

官方文档里特意强调了这个原则：推荐断言"是什么"，而不是断言"不是什么"。我后来把那条改成了：

expect(response.status).to.equal(200);

一来二去，我现在基本只在「不应该有」这种场景下用 .not——比如检查一个对象不应该包含某个敏感属性，或者接口不应该报错。这种时候否定反而比正向写更自然。

踩了 deep 比较的弯路

有次测试一个复杂对象的返回值，我写了：

expect(result.user).to.equal(expectedUser);

结果测试一直红。我百思不得其解——console.log 出来看着一模一样啊！后来翻Chai文档才知道，.equal 默认是严格相等，对于嵌套对象需要用 .deep.equal 做深度比较。

expect(result.user).to.deep.equal(expectedUser);  // ✅ 深度比较

加上 .deep 之后绿灯瞬间亮了。这种修饰器链式组合的写法很灵活——.not.deep.equal、.deep.include 都能混着用，顺序还不影响结果。

关于配置，我只动了一个地方

Chai 有三个全局配置项可以调——includeStack 控制要不要堆栈、showDiff 控制复杂对象比较时要不要显示差异、truncateThreshold 控制长字符串截断阈值。

我试了一下默认配置，发现 showDiff 默认就是开的，那 diff 高亮确实好看——对比两个数组差异的时候，会用 + 和 - 标记出哪些项多了少了。这个对复杂对象的调试特别有用，一眼就能看出来哪里不一样。

最后我只改了 truncateThreshold——默认 40 个字符就截断，但我那个用户模块的 JSON 字段多，经常被截得面目全非。改成 0 让它完整显示之后，调试效率又提升了一截。

现在的测试文件长什么样

一周下来，那个原来堆满 console.log 的测试文件变成了这个样子：

describe('用户反馈模块', () => {
  it('应该正确解析嵌套对象', async () => {
    const result = await fetchFeedback();
    expect(result.user).to.be.an('object');
    expect(result.user.profile).to.have.property('name');
    expect(result.items).to.be.an('array').that.has.length.above(0);
    expect(result.error).to.not.exist;
  });
});

跑一遍，全绿。出错了直接告诉我哪一行断言挂了，错误信息清晰到不用猜。

对比一下前后的变化：原来每写一个测试用例要先写五六行 console.log，跑一次手动比对；现在一句 expect 搞定，Mocha 自动把所有用例跑完还给你一份漂亮的报告。

其实这些东西说起来都不复杂——就是一个断言库加一个测试运行器。但真正让我触动的是那种「写代码像说话一样」的感觉。Chai 的链式语法设计得太自然了，to.be.a('string')、to.not.include、to.deep.equal 这些写出来的断言本身就是一段能读懂的句子。

而这份体验的文档维护得也相当用心，从 npm 安装到 TypeScript 配合、从类型判断到修饰器组合，每个 API 都有具体的代码示例和踩坑提醒。我后来几乎所有问题都能在里面找到答案，不需要再去 Stack Overflow 翻了。

说实话，写测试这件事以前在我眼里就是个不得不做的苦差事，现在反倒有点享受——因为我知道每一行断言写出来之后，它能帮我在上线前拦住那些低级到自己都懒得回想的 bug。顺手提一句，这套资料我也在GitHub、Gitee和GitCode三处同步维护，国内网络环境下挑个顺手的就能直接访问。
