OpenClaw 版本进化史：这只龙虾从 CLI 工具长成多渠道 AI 助手用了多久

软件下载 2026-10-16 ·约 7 分钟 ·老杨

从命令行玩具到常驻后台的多渠道 AI 网关，OpenClaw 的版本迭代节奏藏着它的产品策略。我跟踪了它几轮更新，聊聊那些变化背后的取舍。

现状：一只什么都能接入的龙虾

它的官网上一句话概括了现在这版 OpenClaw：它把 AI 能力包进了一个常驻后台的网关里，然后给你接好了 Telegram、WhatsApp、Discord、Slack 等一整排聊天渠道，模型侧同时顶着三十多家提供商的接口——从 Anthropic、OpenAI 到国内的 DeepSeek、月之暗面、火山引擎，甚至本地 Ollama 端点都行。

我第一次装的时候还是半信半疑：真有软件能把这么多渠道和模型捏在一起不打架？跑起来之后发现它的 doctor 命令比我想象的还要忙——配置键迁移、凭据校验、连通性检查，每一项都在替用户擦屁股。这是我对它最新版本最深的印象：迭代快到配置键都会过期，但它自己知道怎么帮你搬。

来路：从哪里起步

样本文档里没有写早期版本的 changelog，连最初的版本号都没提。我翻了一圈安装和更新的说明，从几个细节里能拼出一条线索。

首先，安装包从下载拿，它同时保留了 npm 全局包和 git 源码两种路径，而且更新命令可以直接在两者之间互切——这通常意味着项目从一开始就是开发者导向的，先有源码再包成发布渠道。守护进程的支持跨 macOS LaunchAgent、Linux systemd、Windows 计划任务、Docker 四种，覆盖密度很高，但文档里的优先级一目了然：先 Linux/macOS，Windows 是后跟上的，回退方案才是启动文件夹登录项。

更有意思的是它的更新节奏：官方文档明写着"一个月出现十来个版本号是常态"。这个密度在同类工具里不算常见——很多 AI 助手项目更保守，大版本之间隔很久。OpenClaw 选择快速推小版本，说明它在跟上游跑：模型提供商的接口变了、某个渠道的 API 改了，它就得跟着调。

关键转折点：功能什么时候长出来的

群聊两层检查这套机制，是我觉得最能体现它成长逻辑的设计。

文档里说群聊同时受「群组允许列表」和「发送者允许列表」两层检查，很多新手只配了一层就栽了。还有 requireMention 默认推荐永远开启，上下文可见性分三档（all / allowlist / allowlist_quote），公开群里可以把陌生人的消息挡在模型上下文之外——这些功能不是第一天就有的。早期版本可能只支持私信，后来用户开始往群里拉机器人，才逼着它长出群聊隔离、提及触发、上下文过滤这一整套。

模型支持的扩张路线也能看出优先级。最早可能只接了 OpenAI 和 Anthropic 两家国际巨头，然后 DeepSeek、Qwen、月之暗面这些国内选项一个个补进来，再后来加了 Groq、Mistral、xAI，最后才是 OpenRouter 这种聚合层。本地端点（Ollama、vLLM、SGLang）是另一条线，官方在 FAQ 里专门说了本地模型和云端旗舰的取舍——这意味着它同时在服务两类用户：想省钱的和想隐私的。

守护进程从可选变成标配是另一个转折点。新手引导现在自动带上 --install-daemon 参数，说明常驻后台已经不是进阶用法，而是默认行为。早期版本可能只是个前台跑的 CLI 工具，用户得自己用 nohup 或 tmux 挂着——当心跳、定时任务、渠道消息这些功能加进来之后，不常驻就等于这些功能全废，守护进程于是从"可选"变成了"必须"。

迭代规律：他们一直在死磕什么

从这些版本里我摸出一个节奏：OpenClaw 的团队一直在死磕边界——渠道边界、安全边界、模型边界。

渠道边界：每个群组天然按群 ID 隔离，论坛话题再加话题 ID 细分，多用户场景配合会话隔离。这不是一句"支持多渠道"就完了，而是真的考虑了多个群、多个人、多个话题同时在用时怎么不串话。

安全边界：密钥不进提示词、不进日志、不进工作区文件；群组默认全拒（故障关闭），直到显式放行；配对只授予私信访问，群组授权必须单独配置。这些默认值的选择说明团队踩过坑——有用户把密钥写进提示词、有用户不小心把机器人暴露在了公开群里。

模型边界：故障转移链、主模型失败自动切后备、心跳等高频轮次单独走一条线——这些都是在解决"模型提供商挂了怎么办"的问题。官方推荐"用最新一代中能力最强的模型"，背后其实是对弱模型的工具调用能力不信任。

什么东西他们一直没怎么动？去OpenClaw文档翻你会发现，它还在教你手动配置群 ID、手动设置 doctor --fix 之后重启服务、手动迁移数据目录到新电脑——这些运维层面的用户体验，他们似乎更倾向于给个命令让你自己跑，而不是做一层更友好的交互。

预判：照这个路线，下一步大概是什么

先说清楚，这只是从迭代规律推的，不是官方口径。

一个月十来个版本号的节奏说明他们在追上游变化，但快速迭代也意味着有些功能是匆忙接上的，群聊规则那页文档开头就说"群聊是配置错误的重灾区"——如果接下来版本里他们能把配置流程做一层向导式的校验，让常见错误在配置时就被挡住，那会比现在纯靠 doctor 事后迁移体验好很多。

模型侧的另一条可能是本地端点的进一步深化。FAQ 里提到"日常闲聊走本地，重活走云端"的混合配置，但目前还得手动切。如果能让网关自己判断对话复杂度、在本地和云端之间自动路由，那会是一个不小的卖点——很多用户对"全本地"有执念，但实际需要云端能力的时候又不想手动切。

Windows 用户的地位大概率会继续慢慢往上提。目前守护进程的回退方案还是启动文件夹登录项，计划任务是优先方案但配置体验跟 Linux 的 systemd 差远了。如果能给 Windows 也做一个更完善的服务管理界面，应该能吃到一批用 Windows 当服务器的用户。

收尾

这只龙虾走到今天，靠的不是某个单点的大招，而是一直在跟上游跑、一直在填边界上的坑。迭代快是好事，但也意味着配置键过期、通道切换这些运维细节用户得自己盯着——好在 doctor 命令已经在帮忙擦屁股了。
