我把 ChatGPT5.6 插进了每周一的例行工作流里

下载 2026-10-16 ·约 8 分钟 ·老杨

以前周一上午要开三次浏览器、手动搬四次数据、等半小时导出。现在一条链跑完，我只需要在最后确认一眼。讲讲具体怎么接的。

每周一上午十点前，我需要出一份上周五产品评审的复盘材料——这份东西是给部门周会用的，内容包括：会议记录摘要、决议事项清单、待跟进任务分配、以及一页风险提示。以前这套流程我手动跑了半年，每一步都在不同的工具里切换，光是复制粘贴就有七八次。

让我先说说旧流程有多磨人。

旧流程的三个断点

第一步，会议记录在飞书文档里。上周的会议开完后，助理会把录音转写成一份 3000 多字的逐字稿，丢在一个共享文档里。我要先打开飞书，找到对应那篇，从头到尾读一遍，把讨论过的议题、每个人的发言要点、最终拍板的结论分别摘出来，整理成三栏的表格。这一步大约要 40 分钟，其中 20 分钟是在反复切换窗口——飞书文档、我的本地 Markdown 编辑器、还有浏览器里查某个术语的定义。

第二步，决议事项要同步到项目管理工具。我们用的是一个开源的看板系统，每个决议对应一条任务卡，需要手动填标题、负责人、截止日期、优先级。以前我是从整理好的表格里一行行抄过去，碰到负责人是新同事还得查一下他的项目编号。这步又耗 25 分钟，其中 10 分钟是在等看板系统加载——它偶尔会卡住刷新半分钟。

第三步，出那份一页纸的风险提示。这需要我把决议里涉及到的依赖关系串起来——比如 A 任务卡在 B 的接口上，而 B 的接口要等外包团队周一才能交付。我得翻一下上周的风险台账（在一个单独的 Excel 文件里），看看有没有历史遗留的风险和这次的决议重叠，然后写成一段不超过 300 字的风险摘要。这步最快也要 15 分钟，因为要打开 Excel、定位到上周那行、比对内容。

三步加起来，80 分钟起步，经常因为某一步卡壳拖到一个半小时。最烦的是任何一步出错，后面的全部要返工——比如会议摘要里漏了一个决议，看板上的任务就少一条，最后风险提示里的依赖链也跟着断掉。

新流程：把 ChatGPT5.6 插在中间

现在的做法是，我把 ChatGPT5.6官网 上的 API 当成这套流程的"中间件"——前面接飞书文档的导出，后面接看板系统和风险台账的 API。具体链路是这样的：

  1. 每周日晚上，飞书有一个自动机器人把当周所有会议的逐字稿打包成一个 JSON 文件，存进我团队的共享网盘。这个 JSON 里每条记录带会议 ID、开始时间、议题标签，结构化程度刚好够程序处理。
  2. 周一早上，我写的一个 Python 脚本会自动下载这个 JSON，然后调用 ChatGPT5.6 的 Responses API——API Key 是从 官方下载 页面注册拿到的——把每篇逐字稿送进去，让它输出一份结构化的摘要。我用的是 GPT-5.6 Terra 规格——不是 Sol，因为这步是批量处理，每篇逐字稿大约 15000 token 输入，Terra 的 medium 推理档位足够把讨论要点、决议、待办分清楚，而成本只有 Sol 的十六分之一。
  3. ChatGPT5.6 输出的不是 Markdown 也不是纯文本，而是我预先定义好的 JSON Schema——里面有 summary（摘要段落）、decisions（决议数组，每项带标题、负责人、截止日期、优先级）、dependencies（依赖关系数组）、risks（初步风险判断）。这个 Schema 我写在一个单独的文件里，调用时直接传进 API 的 response_format 参数——这些字段的约束写法我是从 ChatGPT5.6文档 里翻到的。
  4. 拿到这份 JSON 后，脚本自动完成后面的事：决议数组逐条调用看板系统的创建接口，风险部分和上周台账做 diff，有新增或变化的自动标注，最后把所有内容拼成一份结构化的 Markdown 复盘稿，存进飞书文档的指定目录。
  5. 我只需要在十点前打开那份 Markdown，扫一遍决议里的负责人有没有排错、风险判断有没有明显的漏项，然后提交到飞书。

整条链从脚本启动到 Markdown 生成完，大约 8 分钟。我真正动手的环节只有最后那 3 分钟的人工核对。

两个最容易断链的环节

这套流程跑了六周，中间出过两次问题，让我对衔接点做了两个加固。

第一个断点是飞书转写稿的格式波动。有时候助理录音的环境音比较大，转写稿里会出现大段的噪声文字，或者某几个人的发言被合并成一段。我一开始没处理这个，直接把整段送进 ChatGPT5.6，结果 Terra 偶尔会把噪声段当成有效讨论内容，在决议里凭空造一条。现在我在送进 API 之前加了一道预清洗——用 Luna 规格跑一遍预检，让它判断"这段文本是否为有效会议内容"，置信度低于 0.6 的段落直接丢弃。Luna 的 low 推理档位做这个判断绰绰有余，而且每次预检只花几秒钟、成本几乎可以忽略。

第二个断点是看板系统的 API 限流。我们团队用的那个开源看板，对外部创建请求有每 10 分钟 30 条的硬限制。上周三会开完后有 47 条决议，脚本一口气调用时在第 31 条被拒绝了。解决方案很简单——在调用循环里加了一个指数退避：每次被限流后等 30 秒，再试，最多重试 5 次。如果还是不行，脚本会把失败的决议存到一个本地队列文件里，等下次运行时先处理队列里的积压项。

效果、以及什么时候不该这么做

六个星期跑下来，这套流程给我最直观的感受不是"省了多少时间"，而是"少了两次手动复制"——以前要从飞书文档复制到本地编辑器、再从编辑器复制到看板系统、再从看板复制到风险台账，中间任何一次粘贴错列都要回退重跑。现在 ChatGPT5.6 输出的 JSON 直接喂给两个下游系统，中间没有人工搬运环节。

时间上也确实省了不少。以前周一上午的复盘任务要占 80 分钟，现在总共花 11 分钟（8 分钟脚本 + 3 分钟人工核对）。省下来的时间我用来做下一周的技术选型调研，这是以前挤不出时间做的事。

但这套流程不是什么时候都划算。有两个明显的边界：

一是临时的、只有一两场会议的小周。比如节假日回来那周只开了一场 30 分钟的短会，逐字稿才 2000 字不到，我手动整理比跑这套流程更快——光是等待脚本下载 JSON 和调用 API 的时间，手动已经做完了。这种周我就跳过脚本，手动来，大约 15 分钟搞定。

二是涉及敏感讨论的会议。比如上周有一场关于团队架构调整的闭门会议，转写稿里有几位同事的绩效敏感信息，我不会把这份逐字稿送进外部 API。这种情况我手动整理，或者用本地部署的轻量模型做摘要，ChatGPT5.6 这条链完全不碰。

还有一个隐性的成本是维护。这套流程能跑起来，依赖于几个组件的稳定：飞书机器人不要改输出格式、共享网盘的 API 不要换认证方式、看板系统的限流规则不要收紧。我花了大约两天时间把脚本的错误处理、日志、队列机制都补全了，但以后如果某个上游环节变了，我得再花时间调。这是所有自动化工作流的共同代价——省掉了重复劳动，但引入了维护劳动。

不过目前来看，每周省 60 分钟换来每月可能花 1 小时维护，这笔账是划算的。

如果你也想把 ChatGPT5.6 插进自己的工作流，建议从一个断点开始——先挑那个你手动重复最多的环节，用 Luna 做低成本的预检层，Terra 处理主任务，Sol 留给最复杂的那 10%。别一开始就想做一条全自动的流水线，先让它帮你省掉一两次复制粘贴，跑通了再往前推。

顺便说一句，我上面提到的这套脚本和配置文件都同步放在了 GitHub 上，国内访问不方便的朋友可以去 Gitee 或 GitCode 拿，内容完全一样。
