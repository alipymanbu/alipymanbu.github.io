Kali Linux 踩过的那些坑——从 dpkg 锁到 OpenVAS 初始化

手机版 2026-10-16 ·约 11 分钟 ·老杨

用 Kali 两三年，升级中断锁死 dpkg、公钥过期、工具版本不兼容这些毛病都踩过。把遇到的症状、根因和解法整理出来，省得你再挨个撞墙。

kali linux官网上列着它是专为渗透测试场景打造的 Debian 衍生发行版，看着是个装完就能打命令的渗透工具集，其实上手两三个月你就会发现——它比普通发行版矫情多了。升级稍微断一下、仓库公钥换了、甚至一个工具自己迭代了新版本，都能给你搞出一堆莫名其妙的问题。我第一次遇到 dpkg 锁死的时候以为系统废了要重装，折腾了半天才发现三行命令就能救回来。下面把我踩过的几个比较典型的坑写下来，照这个来省不少时间。

坑一：升级中途断了，dpkg 被锁死

这是 Kali Rolling 用户最常碰上的。apt full-upgrade 跑了一半断电、Ctrl+C 或者网络断了，再来就报「dpkg is locked」或者「could not get lock /var/lib/dpkg/lock」。

E: dpkg was interrupted, you must manually run 'sudo dpkg --configure -a'

症状就是 apt 什么都装不了、什么都更不了，整个系统包管理瘫痪。

原因也简单——升级到一半 dpkg 还在处理某个包，突然中断后它留下了一个锁文件（通常在 /var/lib/dpkg/lock-frontend 或 /var/cache/apt/archives/lock），但进程早就没了。新的 dpkg 启动时看到锁文件就以为有另一个实例在跑，不敢接着干。

解法三步就好：

sudo dpkg --configure -a
sudo apt install -f -y
sudo apt full-upgrade -y

第一行让 dpkg 把上次没处理完的包接着配置完，第二行修依赖，第三行重新升级。跑完基本就活了。我第一次看到这个还不信，以为要删锁文件，但删锁文件容易搞坏包状态——dpkg --configure -a 才是正道，它会自己判断哪些包处理了一半。

如果连 dpkg --configure -a 都报锁，那说明还有残留进程：

ps aux | grep dpkg
sudo kill <PID>

找到那个僵死的 dpkg 进程杀掉再跑 configure 就行。

坑二：仓库公钥过期，apt 全红

某次升级突然变成这样：

W: GPG error: http://deb.debian.org/debian bullseye InRelease:
The repository is not signed.
E: The repository ... does not have a Release file.

或者报「NO_PUBKEY XXXXXXXX」。这时候你以为是网络问题，ping 一下仓库发现通的，但 apt 就是不认。

原因是 Kali 升级仓库时换了新的 GPG 公钥，旧系统还拿着老 keyring 包，验签通不过就拒接所有包。Kali Rolling 每半年一次的大版本快照（比如 2025.1、2025.4）经常伴随 keyring 更新，老系统滞后一两个版本就容易踩上。

解法也直接：

sudo apt-key update

如果这个命令也跑不通，直接装新的 keyring 包：

sudo apt install -y kali-archive-keyring

装完之后 apt update 就能正常刷新包列表了。这个坑我踩了两次，第二次是从 2023.x 直接升到 2025.x 跨了两个大版本，keyring 彻底不兼容。现在养成习惯，升级前先手动更一下 keyring 包。

坑三：工具升级后坏了，想回退又回不去

某次 full-upgrade 把 nmap 从 7.94 升到 7.95，新版本 nmap --script smb-vuln-ms17-010 就报错说脚本找不到。或者 searchsploit 升级后数据库对不上，查出来的 PoC 编号复制过去就失效。

症状就是某个你常用的工具，突然某个参数报错、某个脚本没了、某个功能行为变了，搞得扫描流程跑不通。

原因是 Kali 的 Rolling 仓库跟得很紧，工具作者偶尔会改参数名、移除旧脚本或者重构内部逻辑，而你的渗透流程是在旧版本上调好的。这个在渗透测试场景里挺烦的——报告模板里写着用某个脚本，结果脚本没了，临时改参数又怕扫出来的结果有差异。

解法分两种情况。如果你就想把某个工具钉在当前版本：

sudo apt-mark hold nmap

这样以后 full-upgrade 都不会碰 nmap。要解锁就 apt-mark unhold nmap。

如果想临时降级到历史版本：

apt-cache madison nmap        # 查看仓库里有哪些版本
sudo apt install nmap=7.94-1  # 装指定版本

降完之后建议先 hold 住，不然下次 full-upgrade 又给你升上去。

我现在的策略是：高频依赖的工具（nmap、searchsploit、msfconsole）在稳定工作后统一 hold，等半年的大版本快照发布时再集中解开升级一次。测试工具够用就行，追着最新版本跑反而容易踩坑。

坑四：OpenVAS 初始化慢到让人以为卡死

第一次装 OpenVAS 跑 gvm-setup，我从官方下载拿到的镜像里自带的工具集其实已经够用了，但还是想折腾一下这个大名鼎鼎的扫描器。控制台滚了几分钟之后停在某个地方不动了。等了十分钟还是没反应，Ctrl+C 重来，还是卡同一个位置。我以为是国内网络拉不动漏洞规则库，加了代理也没用，最后怀疑 OpenVAS 是不是烂了。

症状就是 gvm-setup 跑完启动后，访问 https://localhost:9392 打不开，或者打开了但漏洞规则列表是空的。正常情况 OpenVAS 要从 Greenbone Networks 拉 5 万+ 条漏洞规则，这个过程在国内网络下特别慢，还容易断。

原因就是规则库下载。OpenVAS 的规则数据源在海外，国内直连能跑到几 KB/s 的速度，下载几小时都有可能中途断掉。而且即使下载完了，首次启动时还要编译、索引这些规则，CPU 占满十分钟以上，看起来像卡死。

解法也简单，但需要耐心：

sudo gvm-setup --fast-import

--fast-import 跳过一些非必要的同步步骤，首次初始化能快一些。如果还是慢，挂代理或者多等会儿——OpenVAS 初始化本来就是个慢活，别看到不动就重启。

还有个省事的办法：如果不做合规要求的正式漏洞评估，日常用 Nmap NSE 脚本或者 Nuclei 模板扫描就够了。Nmap 的 NSE 漏洞脚本（比如 smb-vuln*、http-log4shell、ssl-heartbleed）覆盖的常见漏洞比你想象的多，而且启动就是秒级的，不用等 OpenVAS 初始化。更多脚本组合和参数细节可以查kali linux文档。

坑五：Volatility 装了两个版本，命令名搞混

Kali 仓库里 Volatility 2 和 Volatility 3 是两个独立的包。Volatility 2 是 Python 2 时代的，插件多、社区资源老文章里常见；Volatility 3 是 Python 3 重写的，速度快但插件体系重构过，有些 V2 插件还没迁移过去。

症状就是你照着一篇 2021 年的内存取证教程跑命令，vol.py 找不到 windows.hashdump 或者某个插件报「Unsupported plugin」。又或者装了 V3 但教程里全是 V2 的命令行参数格式，对不上。

原因很简单，两个版本的命令名、插件体系都不一样。V2 命令是 vol.py -f image.raw windows.pslist，V3 命令是 vol -f image.raw windows.pslist（少了 .py）。而且 V2 有不少社区插件只在旧版上跑，V3 重写后这些插件没迁过来。

解法就是两个都装上，根据文档年代选版本跑：

sudo apt install volatility volatility3

V2 的可执行文件叫 vol.py，V3 的叫 vol，不会冲突。查文档时如果看到命令是 vol.py 开头的就是 V2，vol 开头的大概率是 V3。

防坑清单

用了两年多整理下来，这几件事做到位，大部分坑能绕开：

  1. 升级用 apt full-upgrade 不用 upgrade——Kali 工具集迭代快，旧包被替代时 upgrade 处理不了依赖
  2. apt update 先于 full-upgrade，看到公钥相关警告先跑 apt install -y kali-archive-keyring 再升
  3. 高频工具稳定后 apt-mark hold，等大版本快照时集中解开升级
  4. gvm-setup 跑的时候别碰它，OpenVAS 首次初始化就是慢，网络不好的话先挂好代理
  5. Volatility 两个版本都装，照着命令名判断跑哪个

知道这些坑之后，Kali Linux 其实相当省心。它毕竟是专为渗透测试场景打磨的发行版，工具链的整合度和更新速度是普通发行版比不了的——前提是别踩到上面那些小毛病。这些排查思路和操作记录我也分别同步到了GitHub、Gitee 和 GitCode，方便随时对照查阅。
